# 07 — Iteration Workflow / 迭代工作流

## 1. 目标

工作流服务于两件事：

- Codex 可以快速实现小而完整的可玩增量。
- 人类可以在关键节点直接试玩和判断，而不是被迫填写庞大证据系统。

自动检查负责“没有明显工程错误”；人工试玩负责“是否好玩、好读、好听、想继续”。两者不能互相冒充。

## 2. 每次会话开始

主 Agent 按顺序：

1. 阅读 `AGENTS.md`。
2. 阅读 `CODEX_GOAL.md`。
3. 阅读 `DEVELOPMENT_TASKS.md`。
4. 阅读当前任务引用的设计文档。
5. 运行 `git status --short`。
6. 查看近期相关提交和实现。
7. 确认依赖已完成。
8. 将唯一当前任务改为 `In Progress`。

开始报告只需说明：

- 当前里程碑。
- 本轮任务。
- 范围边界。
- 预计运行的验证。

不要重复整份设计文档，也不要再次询问已有答案。

## 3. 标准实现循环

```text
读取任务与现状
→ 找到最小可逆实现
→ 修改数据/代码/场景
→ 运行快速检查
→ 启动最短可玩路径
→ 根据真实结果修正
→ 更新测试与文档
→ 运行完整适用检查
→ 更新任务状态
→ 主 Agent 提交
→ 报告
```

优先产出可见的小闭环。例如：先让订单终端能显示并接取一份订单，再考虑动画；先让飞船有可调推力与重力，再做最终粒子。

## 4. 检查层级

### Level 0 — 编辑中快速检查

适合每次小修改：

- 编辑器/语言服务器错误。
- 相关单元测试。
- 当前场景直接运行。

### Level 1 — 仓库检查

完成任务前运行：

```bash
./scripts/check_project.sh
```

预期包含：

- Godot 版本/可执行文件检查。
- Headless import。
- 测试运行器。
- 场景烟雾测试。
- `git diff --check`。

### Level 2 — 最短玩法烟雾

根据任务运行：

- 大厅任务：从站点入口到目标交互。
- 驾驶舱任务：从接单状态进入驾驶舱并结束旅行。
- 飞行任务：直接进入 Flight Lab。
- 赤砂星任务：从相关检查点跑到下一阶段。
- 存档任务：保存、退出、继续。

记录实际观察，不需要录入复杂机器证据。

### Level 3 — 人工体验 Gate

只在预定节点执行完整试玩：

- Gate A：大厅接单。
- Gate B：飞行手感。
- Gate C：赤砂星完整路线。
- Gate D：M0 完整闭环。

到达 Gate 后停止扩范围。

## 5. 人工试玩包

主 Agent 提供：

```markdown
## Build / Commit
<commit hash or working tree note>

## How to run
<exact command>

## Start path
<menu/scene/debug route>

## Expected play time
<rough range>

## Focus questions
1. ...
2. ...
3. ...

## Known limitations
- ...

## Reset / retry
<keys or steps>
```

不要求用户填写几十项表格。反馈可直接是自然语言，主 Agent负责整理到任务与 Decision Log。

## 6. 飞行调参循环

飞行改动使用 Flight Lab：

1. 选择固定环境预设。
2. 重置到相同初始位置和速度。
3. 只改变一组相关参数。
4. 测试低速、俯冲、拉起、刹车、高速和碰撞。
5. 记录感受与关键数值。
6. 再决定是否提升为默认值。

避免一次同时改重力、推力、相机和关卡尺寸，导致无法判断原因。

推荐比较：

- 辅助 0%、75%、100%。
- 普通推力与 Boost。
- 空间与大气。
- 空载/当前剧情货物。
- 正常路线与紧急拉起。

## 7. 任务状态更新

### `Done`

只有在：

- 范围实现。
- 验收标准满足。
- 自动检查通过。
- 非人工 Gate 或人工 Gate 已明确接受。

时使用。

### `Human Check`

自动检查已通过，但需要用户判断。主 Agent不得自行改成 Done。

### `Blocked`

说明具体依赖或错误。不要用 Blocked 代替“我不想继续排查”。

### 发现额外问题

- 阻塞当前验收：在当前任务修复。
- 非阻塞小问题：记录为后续任务/已知问题。
- M1/远期想法：写入 Scope 或 Decision Log，不顺手实现。

## 8. Git 工作方式

### 提交者

- 仅主 Agent 提交。
- 子 Agent/并行 Agent 可以研究或修改隔离工作区，但最终由主 Agent审查、测试和整合。

### 提交时机

- 一个任务或可解释增量完成。
- 检查通过。
- 任务状态已更新。
- 不包含无关用户改动。

### 提交信息

优先中文、动词开头：

```text
初始化 Godot 2D 项目与像素显示设置
实现大厅玩家移动与通用互动
加入赤砂星雷达扫描与低飞遮挡
修复返航后订单状态重复触发
```

避免：

```text
update
fix stuff
WIP
final
```

### 提交前清单

```bash
./scripts/check_project.sh
git diff --check
git status --short
git diff --stat
```

核对：

- 没有 `.godot/`、日志、导出构建。
- 外部素材已更新 `ATTRIBUTION.md`。
- 新依赖已更新 Dependency Log。
- 玩家文本没有直接硬编码。
- 没有把无关重构混入功能提交。

## 9. 新依赖流程

1. 描述当前问题。
2. 尝试 Godot 内置能力或小型自有实现。
3. 比较候选依赖。
4. 在 `09_DEPENDENCY_LOG.md` 记录。
5. 仅在理由充分时安装。
6. 加入最小使用面和移除说明。
7. 运行完整检查。

不要为了省几十行代码引入会长期控制数据格式的大型插件。

## 10. 文档维护

更新规则：

- 产品事实改变：更新 Narrative Bible / Game Vision / Decision Log。
- M0 范围改变：更新 CODEX_GOAL、Demo Scope 和任务列表。
- 技术架构改变：更新 Technical Design 和 Decision Log。
- 任务实现细节：优先由 Git 表达，只在任务状态中简短记录。
- 新第三方内容：更新 Attribution/Dependency Log。

README 保持入口性质，不堆叠所有任务日志。

## 11. 问题处理

### Godot 无法启动/导入

- 确认 Godot 版本和 `GODOT_BIN`。
- 查看首个真实错误，不被后续级联错误淹没。
- 使用 headless import 重现。
- 检查资源路径大小写和丢失 UID/引用。

### 场景可运行但测试失败

- 不通过删除测试解决。
- 判断测试是否描述当前合同。
- 若设计决定改变，先更新文档和测试，再改实现。

### 手感不好但自动测试通过

- 自动测试只证明公式边界。
- 返回 Flight Lab，调整最少参数。
- 到 Human Gate 前不批量制作关卡。

### 内容看起来不一致

- 先检查 Art Direction 与像素密度。
- 不用更多滤镜掩盖问题。
- 将资产降级为 placeholder 并重新处理。

## 13. 不采用的旧式流程

本项目不建立庞大的人工证据录入、几十项截图门槛、复杂状态报告生成器或为了验证而验证的工具链。

仅保留：

- 一个快速仓库检查入口。
- 有价值的自动测试。
- 简洁人工试玩包。
- 清楚的 Git 历史。
- 关键决策日志。

工具只在明显减少重复劳动时新增。
